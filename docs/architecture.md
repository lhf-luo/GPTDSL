# 架构草案

## 当前与目标

当前：uv 管理的 Python 项目，已实现补丁筛选、补丁上下文准备模块及 CLI，其他模块仍为目录和说明文件。

目标：由 workflow 调度六个职责独立的业务模块，局部步骤可接入 agent。

```text
Git 历史 → 补丁筛选 → 补丁与上下文准备 → 缺陷模式提炼 → QL 查询合成 ⇄ 查询验证 → 泛化评估
```

这是逻辑数据流。实际重试、回退与停止条件由 workflow 管理。

## 六个业务模块

| 模块 | 输入 | 输出 |
| --- | --- | --- |
| patch_selection | 本地 Git 仓库、历史范围或提交清单、筛选预算、可选复核器 | 初筛候选、入选提交清单、带理由和证据的筛选报告 |
| patch_context | 修复补丁、提交信息、源码位置 | 补丁与相关源码上下文、版本信息 |
| pattern_analysis | 已准备的补丁及上下文 | 缺陷模式、修复意图、检测条件及适用范围 |
| query_synthesis | 检测条件、语言参考、验证反馈 | 候选 QL 查询及辅助文件 |
| validation | 候选查询、回归样例及分析数据库 | 编译与执行结果、修复前后差异、反馈 |
| evaluation | 已验证候选、独立标注样例 | 检测指标、误报漏报记录与评估条件 |

补丁上下文模块已提供 `prepare_patch_context(repo, commit, *, limits=None)`，
返回带历史来源信息、前后函数与诊断的 `PatchContext`。
筛选模块提供 `select_patches(repo, revision=None, *, commit_file=None, limits=None, reviewer=None, progress=None, previous=None)`，
默认扫描 HEAD 历史；显式提交清单按行处理，不展开历史。两个输入互斥。
返回 `SelectionResult`；其余模块的具体数据结构留待实现。

筛选采用确定步骤：Git 元数据和规模检查 → 上下文准备 → 可选 AI 质量复核 → 本地证据校验。
AI 通过 `Reviewer.review(context)` 返回结构化结论，由选择器校验引用的版本、文件、行范围、
源码内容及展示可见性。离线候选不会自动入选；标签和关键词不是入选依据。
初期语义范围为错误处理与局部资源清理，不进行漏洞严重性或利用价值排序。
CLI 利用逐项进度回调保存已完成前缀，提供 Ctrl+C 保存与 `--resume` 续跑；
筛选器保留只读、无内置文件写入的性质。断点层检查输入与复核配置，使用报告快照恢复，
不会自行重试已经记录的错误项。

## 依赖边界

- workflow 组织阶段调用，管理状态、预算、有限重试和结果记录。
- 业务模块不互相控制执行顺序，不直接调用 workflow。
- 明确复用关系：`patch_selection → patch_context`，用历史上下文判断材料是否足够；
  `patch_context` 不依赖筛选模块。CLI 负责参数和导出，选择器本身不写文件。
- 查询合成接收验证反馈，由 workflow 负责传递；不自行修改验证规则。
- 筛选模块已提供可配置的 Chat Completions adapter，默认离线；CodeQL 接入留待后续阶段。
- 验证区分查询问题、数据库覆盖问题和外部环境问题。
- 最终独立评估结果不参与该轮候选的调优。
- 暂不创建通用 agent 框架、插件系统或共享抽象层。

## 实施顺序

1. 已完成：初始化、只读历史上下文收集，以及有界 Git 历史筛选和可选语义复核。
2. 后续阶段：围绕一个受限补丁类别实现模式提炼、查询合成与回归验证。
3. 获得失败记录后，再决定哪些步骤需要 agent 自主补充上下文。

## 实验记录要求

后续实现应记录源码提交、构建配置、CodeQL 版本、模型配置和候选修改历史。
修复回归与独立评估应使用明确区分的样例集合，指标需注明统计粒度。
